# Changelog

Notable changes to resume-builder, newest first. Requirement and decision ids (such as R7.5, B9a, D21) and section numbers refer to the [product requirements](docs/PRD.md).

## Unreleased

- Internal (#7, B8): new `App.context(actor, user, channel)` builds a request context in the App's own tenant. Bootstrap, the sync watcher, `rb mcp`'s pre-sync, the CLI, the HTTP API and the website now all use it, so an App serving a tenant other than `local` no longer refuses its own bootstrap and sync calls. No change for a local install.
- **Sync goes through operations** (#5, R7.7a, D40): each changed YAML or Markdown file is now applied with an operation, as you on the `yaml-sync` channel, with the same permission check, validation and audit entry as the same change made with a command. `rb audit` shows them as yours (`application_replace`, `library_replace`, ...) instead of `system` `sync:...`. New operations `settings_replace` (new owner-only permission `settings:write`), `registry_replace`, `library_replace`, `application_replace` and `posting_replace` replace a whole item at once; left-out items are archived and recorded events can't change. Fix: editing a job's `profile.yaml` now flags an approved cover letter or answer as out of date, as a profile change through the agent already did (R9.14). `sync --check` now tries each change through its operation too, and still changes nothing.
- Internal (#6, B3): the authorization policy now belongs to each `App` instead of the whole process. By default an App gets a `RolePolicy` over its own registry's role table; `security.set_policy()` and `get_policy()` are gone, and tests set `app.policy` instead. No change in behavior for users.
- **Fix:** commands that take a file now accept it as your computer sees it: with backslashes, typed from the repo folder (`.\data\<you>\intake\resume.pdf`) or as a full path, as long as it points into your own folder. This covers `rb import-resume`, `rb new-job --file`, `rb resolve` (`jobs\<job-id>\application.yaml` works) and `rb restore` (`.\backups\<you>\<file>` works). Before, only the path relative to your folder with forward slashes worked, and the others gave confusing "not found" errors. A path into another user's folder is still refused, and so is `..`.
- Fix (PDF resumes): bullets whose mark sits on the same line ("•  Automated ...", as in resume-builder's own ATS PDF) and whose wrapped lines come apart are read whole again, using where each line sits on the page: a line indented under the bullet's text continues it, a line at the margin starts the next heading or role. Wrapped paragraphs are joined too. Before, each wrapped line became a broken role. Also: a sentence under a role's dates ("... most recently as QA Manager at ...") is noted instead of read as the title and company, a description before a role's bullets is no longer imported as a bullet, and an unknown heading in capitals ("HOME LAB & PORTFOLIO") ends the skills section and is reported as not imported.
- **Word and PDF resumes** (#39, R2.12, D39): `rb import-resume intake/resume.docx` (or `.pdf`) imports a Word or PDF resume saved in your intake folder, as drafts like any other format. Word keeps headings, bullet lists and tables; a PDF keeps its text, with bullets and wrapped lines put back together, and the report reminds you to check the order. Limits: 10 MB per file, 20 PDF pages, 30 seconds to read a PDF; Word files that unpack to too much are refused (zip bombs). The old `.doc` format, scanned PDFs (no text) and password-protected files are refused with what to do instead. Uses `mammoth` and `pdfminer.six` (about 26 MB); MarkItDown, which wraps the same two, would have added about 200 MB to the image.
- **Import your existing resume** (#1, R2.5–R2.11, D38): `rb import-resume intake/resume.html` reads a resume saved as HTML, Markdown or plain text in your intake folder (or `--stdin`), or `rb import-resume <link>` fetches it once, with the same safety checks as a posting link (your resume page, a Markdown or text file, a Google Doc shared with anyone who has the link; a sign-in or JavaScript-only page is refused), and adds its summary, roles and bullets, projects, education, certifications and skills to `base.yaml` as drafts. It shows what it found and asks once. Your words are kept: nothing is reworded, metrics stay empty (bullets that mention numbers are listed), no tags are invented. Existing entries are never changed: new ids, likely duplicates reported rather than merged, new bullets for a role you already have added under it. Companies your registry knows by name or alias get the registry's name; others are suggested with `rb add-company`, never added. Contact details are left out, links listed for `user.yaml`, and sections the library doesn't hold named. Operations `library_import` and `library_import_file` (permission `content:propose`, dry run by default), so an AI agent can import a resume you give it, as text or a link, as drafts only. If the resume changed between the preview and your `yes`, nothing is imported. Skill groups now have a `status` like other items: imported groups are drafts, `rb confirm` and `--all` confirm them, and a group without a status counts as confirmed, so existing libraries render as before.
- Fix: the home page's AI agent card said "No AI agent has connected yet." twice (and repeated the copy-and-paste and unused-token states the same way). Each state is now one message, which `agent_status` returns with its details (the token's issue date, the last copy-and-paste use).
- **Your answers on a job** (#38, R6.6, R6.7, R13.22a, D37): when an AI agent proposes a job, it now asks how interested you are, why you want it, how you found it and any next step, and passes your answers on word for word (`from_user` in `job_intake_propose`). `rb confirm-job` and the website's Proposed jobs page show them as "from you, via the agent" so you can check and change them before the job is created; nothing is saved until you confirm. `rb new-job` takes your answers too: `--set interest_notes="..."`, `interest_level`, `next_action`, `next_action_due`, `notes`. New command `rb set <job-id>` (operation `application_update`) changes your own fields on an existing job (interest level and notes, source, next action and due date, notes, fit summary, outcome reason) without opening `application.yaml`, and writes the change back keeping comments; signed in, the job page has an **Edit details** form for the same. The agent can propose such a change (`application_propose_update`); you see the old and new values and confirm or discard it with `rb update-drafts`, `rb confirm-update <n>`, `rb discard-update <n>` or on the job page. Confirming is refused if you changed that field since. Drafts are kept and resolved once (migration 0006). The agent rules now say the agent passes on your words but never writes them.
- Fix: the cover letter and answer checks refused citations of bullets under `earlier_roles` ("isn't on this job's tailored resume"), although those bullets are on the resume in the "Earlier experience" entry. They count now. The job page's "Compared with your public resume" line counts them too.

- **Ready-made prompts** (#37, R8.13, D36): a new **Prompts** page on the tracker gives a prompt for everything your AI assistant can do (tailor, redo after your answers, cover letter, "why here", a message to the hiring team, add a job, record a recruiter's email, notes to bullets, review bullets, public resume), filled in for your job with a **Copy prompt** button, worded for a connected assistant or for copy and paste (with the `rb brief` and `rb propose` commands around it). The page starts with the wording your AI agent status suggests. Job **Next steps** show the prompt where the next step is the assistant's. Connected assistants get them as MCP prompts (`prompts/list`, `prompts/get`), offered as slash commands such as `/mcp__resume-builder__tailor` in Claude Code. New command `rb prompts [<job-id>] [--name] [--for connected|paste]`; `rb next` shows prompts too.
- **Delete a user** (R10.9a, D35): `rb delete-user <name>` deletes a user's data folder, database and exported files, after listing them and asking you to type the name back (`--confirm <name>` for scripts). It keeps the user's backups and makes a final one first, so `rb --user <name> restore` and `rb --user <name> export-files` bring the user back; `--delete-backups` removes those too. It refuses your default user (`RB_DEFAULT_USER`). New owner-only permission `space:delete` and operation `space_delete`; `Storage` gains `destroy()`.
- **Copy-ready commands** (#36, R8.12, D34): a new **Commands** page on the tracker lists the everyday `rb` commands by task, filled in with your job's id and its latest resume snapshot id, each with a **Copy** button. Each job's page starts with **Next steps**: only the commands and files that fit where that job is (posting, interest notes, tailoring, draft items to confirm, letters and answers to approve and then export, rendering, recording that you applied, then replies and follow-ups). New command `rb next <job-id>` prints the same, and new read operation `job_next_steps` provides them. Every command shown is checked against the real `rb` parser in the tests.
- A short "message to the hiring team" in place of a cover letter: save it as an answer with slug `hiring-team` (user manual, section 9). Its propose, approve and plain-text commands are on the Commands page.
- Fix: a job's answers exported to the same file name (`..._Answer_<job-id>.txt`), so exporting one overwrote another. New answer snapshots record their slug, and the file name includes it (`..._Answer_why-here_<job-id>.txt`). Answers saved before this keep the old name when exported.
- Fix: approving a cover letter or answer suggested `rb export <id>`, a command that doesn't exist; it now says `rb regenerate <id>`.
- Fix: the help pages showed " 97" after links to the repository instead of the ↗ arrow.
- README: says up front that resume-builder is an MCP server, what its tools do, and the two ways to connect.
- AI-AGENTS.md: warns not to enter resume-builder's URL under Claude's or ChatGPT's "Add custom connector" (those connectors run on the provider's servers and refuse local addresses), with a troubleshooting row for Claude's "Enter a public https:// URL" message.
- **MCP over HTTP** (#35, D33): assistants on your computer can connect to resume-builder's tools with a URL, `http://localhost:8000/mcp/<you>`, and an agent token (`rb token --actor agent`), instead of the `docker compose ... rb mcp` command: for example `claude mcp add --transport http resume-builder http://localhost:8000/mcp/<you> --header "Authorization: Bearer <token>"`. It needs the tracker running; the command still works without it. Same tools and checks as stdio; only the agent's token is accepted; a foreign Origin or Host is refused; never reachable from the internet. The AI agent card shows it as "MCP over HTTP". AI-AGENTS.md shows the URL setup for Claude Code, Gemini CLI and VS Code, and how to test it.
- **Online help** (#34, R8.11): a **Help** link on every page of the tracker opens the quick start, the user manual and the AI agent guide in one help window (a second click brings it to the front instead of opening another). Small **?** links open help at the matching section from the sync status, the AI agent card, proposed jobs and the sign-in page, and help has a search box. The guides are rendered on the server from `docs/` (packaged into the image, so they work offline and match your version) with markdown-it-py; raw HTML is escaped, and code blocks are labelled "macOS, Linux" or "Windows PowerShell". The site's Content-Security-Policy now allows the site's own script files (`script-src 'self'`) for the pop-up, and still no inline or third-party scripts.
- AI-AGENTS.md and the user manual: a short "Answering the agent's questions" section: answer in the chat, numbered; real gap or missing information; where each answer ends up (draft bullet to confirm, a metric you add to `base.yaml`, your reasons in `interest_notes`); then ask the agent to redo the drafts.
- Fix: the agent brief now gives each confirmed education entry's degree, field and dates, and each certification's issuer and date. It listed only the school or certificate name, so assistants asked for a degree the library already held.
- AI-AGENTS.md: step 3 (connect your assistant) starts with a table of every assistant, how it connects and a link to its setup section. The MCP command and what its parts mean moved to step 4, where you test it.
- AI-AGENTS.md and the quick start show every command for both macOS/Linux and Windows PowerShell: working folders, the MCP command and testing it, saving instruction files (as UTF-8), clipboard copy and paste, the HTTP API example (`Invoke-RestMethod`), and Windows versions of the Claude Desktop, Gemini CLI, Codex and VS Code settings. Commands that are the same everywhere say so.
- AI-AGENTS.md: section 2 is now "Setting up", four steps in order: install resume-builder and add a job, install your assistant, connect it (working folder, the MCP command, standing instructions, or copy and paste), and verify it (test the MCP command, check the tools, then the AI agent card). The separate sections that used to follow it are folded into those steps.
- AI-AGENTS.md: install commands for the terminal assistants are now in one place (section 2), with one method each: Anthropic's installer for Claude Code, npm for Gemini CLI, Codex CLI and GitHub Copilot CLI. Each assistant's setup steps point there instead of repeating them differently.
- Agent status (#33): drafts pasted with `rb propose` no longer make the agent show as "connected". A new state, "Used through copy and paste", says that no assistant has connected directly; "connected" now means MCP or the HTTP API, and names that channel even if you've pasted something since.
- AI-AGENTS.md: a new "Do I need a paid AI plan?" section. resume-builder never needs one: copy and paste works with any free chat assistant. A table shows, per assistant, whether its free plan works with resume-builder's tools (as of November 2026), for example that Claude Code needs a paid Claude plan or API account, while Claude Desktop, Gemini CLI and Codex CLI work on free plans.
- AI-AGENTS.md: every terminal assistant (Claude Code, Gemini CLI, Codex CLI, GitHub Copilot CLI) now starts with installing it and checking that its command is on your PATH, with what to do if it isn't. A new "On Windows" section covers PowerShell commands, paths in JSON and TOML, and saving instruction files as UTF-8 (Windows PowerShell 5.1's `>` writes UTF-16, which assistants may not read). Claude Code also shows adding the server with a `.mcp.json` file for anyone without the `claude` command.
- **AI agent status** (#32, R8.10): the website's home page has an **AI agent** card, and `rb status` a line, saying whether an agent is connected (and through MCP, the HTTP API or copy and paste), when it was last active, the MCP client's name, its last few actions, what's waiting for you, or that a token was issued but not used, or that no agent has connected yet, with setup hints. It also warns when your assistant keeps using an API token you've replaced. New read operation `agent_status`. The app records when the agent last ran any operation on each channel (at most once a minute), audits MCP connections (`agent:connect`, at most once an hour) and use of a replaced agent token (`api:token-replaced`). It never shows a token.
- **Host check on every request** (#31, R8.9): the website and HTTP API now refuse any request whose `Host` isn't `localhost`, `127.0.0.1` or `::1` (any port), before any route runs: pages, API reads and writes, `/docs`, `/openapi.json`, `/health`, snapshot downloads and plugin routes. This closes a DNS-rebinding gap where another website open in your browser could have read your tracker's pages. `RB_WEB_HOSTS` in `.env` adds names; an app embedding resume-builder passes its own list (`web_hosts`).
- **Confirm or discard on the website** (#30, R8.8, R8.9, D32): sign in to the tracker with a one-time link from the new `rb web-login` (valid 10 minutes, once) or an owner token (agent tokens can't), and jobs and events the agent proposed get **Confirm** and **Discard**. Confirming a job uses a form with the same choices as `rb confirm-job`. Without signing in the site stays read-only. The session cookie is `HttpOnly`, `SameSite=Strict`, scoped to your pages and signed with a per-install secret outside your data folder; only hashes are stored (migration 0005); sessions end after 12 hours idle, 7 days, or on sign-out. Every action is a `POST` with a CSRF token, checked for the site's own origin and a local host name. Website pages now send `X-Frame-Options: DENY` and a script-free Content-Security-Policy. Sign-ins, sign-outs and every action are audited, as the owner on channel `web`.
- **Site adapters can read JSON APIs** (#29, R13.7, R13.10, R13.16, D31): `fetch(url, accept="json")` gets an applicant tracking system's JSON API response through the same safe, audited fetcher; only JSON is accepted for that request, and JSON nested too deeply or invalid is refused. The adapter must supply the posting as Markdown, checked block by block: each heading, paragraph and list item must keep the wording of one string in the JSON. Field passages can be quoted from JSON values. Migration 0004 rebuilds `posting_captures` to allow `application/json`, keeping every row, the proposals that refer to them, the index and the append-only triggers. Migrations can now opt in to running with foreign keys off (`-- rb:foreign-keys-off`), checked with `PRAGMA foreign_key_check` before they commit.
- Job intake docs (#27): the user manual now spells out what intake never guesses and that every value is checked against the posting, mentions agent proposals and the `--file` option where you start a job, gives the `intake` settings' defaults, and says what else `SYNC-STATUS.md` lists.
- **Website: proposed jobs and saved postings** (#26, R13.8, R13.23): a new **Proposed jobs** page lists what the agent proposed, with each value, its origin and the passage it came from, the company match, duplicates and the posting as captured, plus the `rb confirm-job` / `rb discard-job` commands; the home page says when any are waiting. The site stays read-only (PRD 8.8), so confirming happens on the command line through the same operations. Each job page shows every saved copy of its posting, newest first, as escaped text (the fetched page is never displayed). New read operation `posting_captures`. Links to postings are made only for http(s) addresses.
- **Jobs proposed by the AI agent** (#25, R13.22–R13.24, D27, D28): an MCP or API agent given a posting link (or text) calls `job_intake_propose`. The app fetches the link itself; every value the agent adds must pass the passage check, or the proposal is rejected. Nothing is created until the owner reviews it: `rb job-drafts`, `rb confirm-job <n>` (the same review and options as `rb new-job <url>`) and `rb discard-job <n>`; waiting proposals also show in `rb status` and `SYNC-STATUS.md`. New permission `application:propose` for the agent, operations `job_intake_propose`, `job_intake_proposals`, `job_intake_confirm` and `job_intake_discard`, and migration 0003 (proposals are kept, resolved once, never deleted). The agent's instructions now say intake is transcription only, never touches interest notes, and treats posting text as data.
- **Intake folder** (#24, R13.2, R13.4, D25): when a posting's site needs a sign-in, save the posting text in `intake/` in your folder and run `rb new-job --file intake/<name>.txt [<link>]`. The review works as with a link. Files there are read only on that command, through the file adapter (operation `job_intake_preview_file`), with the usual safe-reading limits (UTF-8, 1 MB); the app never changes, moves or deletes them. `SYNC-STATUS.md` lists files already used for a job, which you can delete. Bootstrap seeds `intake/README.md` for new and existing users. A page that can't be read now points to this folder.
- **Job intake** (#23, PRD 8.13, D30): `rb new-job <url>` starts a job from its posting link. It fetches the page once, shows a preview (each field with where it came from, the matched company and department, what the posting doesn't state, and any job you already track with the same link or posting id) and asks once before creating the job with `application.yaml` filled in and the posting saved in `posting.md`. `rb new-job --stdin [<url>] < posting.txt` takes pasted text when a site needs a sign-in. `--company`, `--department`, `--create`, `--title`, `--source`, `--set FIELD=VALUE`, `--recapture`, `--allow-duplicate` and `--yes` cover the choices. Without a link or `--stdin`, `rb new-job` works exactly as before. New operations `job_intake_preview` and `job_intake` (owner, `application:write`) in the HTTP API too. The preview stores the capture so confirming never fetches again; confirming checks every field against the posting again and writes registry additions, the application and the posting in one transaction.
- Job intake groundwork (#22): the company and department named in a posting are matched against the organization registry (`match_company`, `match_department`, R13.17), with existing entries offered first and nothing created until the user chooses. A duplicate check (`find_duplicates`, R13.18) finds applications with the same posting link (tracking parameters, `www.`, fragments and trailing slashes ignored; links on saved captures included) or the same company and posting id, archived ones too.
- Job intake groundwork (#21): site adapters as an extension point (`adapters.py`, `ext.add_site_adapter`, R13.16). A plugin can read one site's posting pages; core holds it to the intake checks: it fetches only through the safe, audited fetcher, only from its own domains and at most twice; its Markdown must keep the page's wording; its fields go through the passage check. Documented in ARCHITECTURE.md.
- Job intake groundwork (#20): application fields are extracted from a captured posting, each with the passage it came from (`posting_fields.py`, R13.13–R13.15). schema.org `JobPosting` data is read first, then rules for labels ("Location", "Salary range", "Posted on", "Job ID #", including labels on their own line), salary ranges as posted, and the source from the link's domain. `work_arrangement` is set only when the posting states exactly one arrangement. `verify` is the honesty check for every value, whoever proposes it: the passage must be in the capture and must state the value. Where the structured data and the text disagree, the difference is reported.
- Job intake groundwork (#19): captured pages become `posting.md` without any rewording (`postingtext.py`, R13.11). The main content is converted mechanically to Markdown; navigation, headers, footers, scripts, forms and cookie banners are dropped. Sign-in pages, JavaScript-only pages and near-empty pages are refused with the paste fallback (R13.3); a JavaScript page that embeds schema.org `JobPosting` data uses that posting's own description. `posting.md` gets a Source section and keeps your "My notes". Posting text you pasted or edited is never replaced unless asked, and unsynced edits become a sync conflict (R13.12).
- Job intake groundwork (#18): a safe one-shot fetcher for posting URLs (`fetch.py`, R13.5–R13.9). It checks every resolved address, and every redirect, against loopback, private, link-local and other internal ranges and connects to the checked address; at most 5 redirects; timeout and size limit; HTML or plain text only; no cookies or user data. Fetches are audited with the host only. New `intake` settings in `user.yaml` (`fetch`, `timeout_seconds`, `max_bytes`). The App takes a `fetcher`, so tests use a local stub. No new dependencies.
- Job intake groundwork (#17): captured job postings are stored in the database (migration 0002, R13.10, D29). Captures are append-only, enforced by the schema; every capture is kept. Migrations can now contain triggers.
- One-step setup: `setup.sh` (macOS, Linux) and `setup.bat` / `setup.ps1` (Windows) create `.env` on the first run, then build and start the app and install the `rb` command.
- `rb` without Docker commands: `scripts/install-rb.sh` (macOS, Linux) and `scripts/install-rb.cmd` (Windows) install an `rb` command that runs `rb` in the container from any folder. On Windows it is added to the user PATH without changing anything else in it, and `-Uninstall` restores the PATH exactly.
- PRD: added section 8.13, job intake from a posting URL (default) or pasted text, with decisions D24–D29 (approved November 15, 2026) and the `application:propose` permission for the agent (B2, B7). Not yet implemented.
- Piped input no longer needs a separate `rbi` alias: `rb propose` accepts piped text directly, and ignores the byte-order mark Windows PowerShell 5.1 adds to piped text.

## 0.1.0 (November 13, 2026)

### Agent integrations

- Added the MCP server (`rb mcp`), `rb propose` for pasted drafts, and `rb agent-instructions`. The last keeps one shared copy of the agent rules, which is also sent as the MCP server's instructions. The MCP server and `rb propose` always act as the `agent` actor, so a pasted or tool-submitted draft gets the agent's strict checks and is audited as the agent's work.
- Browser assistants (claude.ai, Gemini, ChatGPT, Microsoft Copilot) can't connect directly because their connectors need an internet-reachable server, and the app only listens on localhost (PRD section 10). They use copy and paste.
- Fixed: the number check in R9.10 matched numbers inside other numbers ("5" in "25"); it now compares whole numbers.

### Implementation notes (first build)

Where the build differs from, or adds detail to, the requirements in the PRD:

- **File watching (R7.5, D21)** uses polling every few seconds (`RB_SYNC_POLL_SECONDS`, default 3) only. Polling behaves the same on every host OS's Docker mounts; native file events were not added.
- **Tokens (B9a)** are issued on demand with `rb token`, not at bootstrap, because a token created at bootstrap could never be shown to the user.
- **Content rules (R4.1)**: a profile that references a *draft* item syncs with a warning. Final rendering refuses it; a preview allows it (R2.3). Referencing a missing item is always an error.
- **Snapshot protection (R12.10)** also covers the current approved version of each letter and answer, so their version ids never dangle.
- **Stage transitions (PRD section 8.6)**: open stages may move forward and skip stages, but never back.
- **PDF determinism (R12.7)**: the PDF identifier is the snapshot id, and `SOURCE_DATE_EPOCH` is set to the snapshot's creation time while rendering, so embedded font subsets carry a fixed timestamp. Verified byte-for-byte in the Docker image test suite.
- **Milestone 6 (publishing)**: `rb publish` exports the public site to `output/<user>/public/`; pushing it to the target is not built.

### Consistency review of the requirements

Fixes made to the PRD before implementation:

1. **Decisions:** D18–D22 were completed but the note above the table still listed them as open. D15 and D16 were still marked open and now take the recommended choice.
2. **Sample resume vs. confirmed-only rendering:** the seeded public profile selects draft example entries, but only confirmed entries may be rendered (R2.3, R10.13). A watermarked preview mode now covers this (R2.3, R10.12).
3. **Per-user schemas:** JSON Schemas list each user's own company slugs (R11.3), so they can't share one `/data/.schemas/` folder. They now live in `/data/<user>/.schemas/` (R10.14).
4. **Agent identity:** RBAC limits the agent (B7), but nothing said how the API knows who is calling. Local actor tokens are added (B9a).
5. **Backup retention:** frequent pre-change backups would have pushed out all the daily ones. Retention is now counted per kind (DK6).
6. **Lifecycle stages:** "withdrawn" couldn't be reached from `interested`, and "rejected" could be reached before applying. The transitions are now explicit (PRD section 8.6).
7. **Concurrent syncs:** the server's watcher and a CLI container could sync at the same time. A per-user lock is added (R7.5a).
8. **Bootstrap on CLI runs:** every `docker compose run` would have repeated the full bootstrap. One-off CLI containers now run only migrations and the quick sync (R10.1).
9. **Default user:** R1.1 required `--user` on every command; it now defaults to `RB_DEFAULT_USER`.
10. **G5 measure:** onboarding also needs `.env`; the measure now says so.
11. **Where the AI runs:** the PRD described AI-generated drafts but never said where the model runs. The app has no built-in model; an outside agent uses `agent-brief` and the API (see Scope in the PRD).
12. **Citation format:** R9.9 required citations without defining them. The `[cite: …]` marker is now specified.
13. **User docs:** the user manual and quick-start guide became part of the first release.
